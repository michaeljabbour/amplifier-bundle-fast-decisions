## 0. Ground truth that changes the brief

Three findings contradict assumptions in the task brief. They are load-bearing: P1, P3 and P4 are
specified differently because of them. Each is reproducible.

### 0.1 No shipped provider implements `.stream`. The streaming regression is not what it looks like.

```
$ ~/.local/share/uv/tools/amplifier/bin/python3 -c '<import each provider, check callable(getattr(cls,"stream",None))>'
AnthropicProvider False    OpenAIProvider False       GeminiProvider False
OllamaProvider   False     VLLMProvider   False       ChatCompletionsProvider False
GitHubCopilotProvider False  ChatGPTProvider False    (azure-openai exports no provider class)
```

`loop-streaming:4614` selects the transport with
`stream_provider = callable(getattr(provider, "stream", None))`. Today that is **False for every
provider with or without our facade** — so `RoutedProvider.__getattr__` hiding `stream`
(`orchestrator.py:50-53`) currently changes *nothing* about which transport runs.

Token streaming reaches the user from **inside** `complete()`: the Anthropic provider iterates the
SDK event stream and emits `llm:stream_block_start` / `_delta` / `_end` on the hook bus
(`provider-anthropic/__init__.py:4190-4230`), which is what `hooks-streaming-ui` renders. Our facade
calls the real `complete()` unchanged (`orchestrator.py:111`), so those events still fire.

`transport: provider-complete` in the DTU is our own label, emitted by us at
`orchestrator.py:197` — it is a description of our design intent, not a measurement of a
regression. **Do not "fix" a symptom that is a string we wrote ourselves.**

### 0.2 The `.stream` transport in loop-streaming cannot execute tool calls at all.

```python
# loop-streaming:6595
async def _has_pending_tools(self, context) -> bool:
    return False                 # "Simplified - would need to track tool calls properly"
# loop-streaming:6600
async def _process_tools(self, context, tools, hooks) -> None:
    ...                          # no body
```

The streaming branch (`4857-4930`) yields text chunks and then asks `_has_pending_tools`, which is
hard-coded `False`. A tool call arriving on that transport is silently dropped. The stream contract
is also text-only: `_stream_from_provider` (`6033-6125`) calls
`provider.stream(chat_request, tools=tools_list)` and reads `chunk["block_type"]` / `chunk["content"]`
— **plain dicts, and there is no `StreamChunk` model anywhere in `amplifier_core`** (grepped;
`content_models.py` has `ToolCallContent`, but it is never produced or consumed on this path).

Consequence: the brief's proposal — "yield the synthetic response through the streaming interface" —
is **unimplementable and unsafe**. There is no chunk shape that carries a `ToolCall`, and if there
were, `_has_pending_tools` would discard it. It would fail *open* into "nothing happens", which is
worse than falling back to the LLM.

### 0.3 There is no alternative interception seam. `complete()` is the only one.

- `provider:request` payload is `{"provider": provider_name, "iteration": iteration}` — no request,
  no messages (`loop-streaming:4318-4321`, `2737`, `3174`, `5418`). A hook cannot see or replace what
  is about to be sent.
- `HookResult` supports `deny` / `inject_context` / `ask_user` / `modify`
  (`amplifier_core/models.py:127-190`), but **loop-streaming does not honor `modify` on `tool:pre`**:
  after `process_hook_result` it only checks `deny` (`6267-6275`) and then executes
  `tool.execute(tool_call.arguments)` with the **original** arguments (`6329`).
- Therefore: a hook can *observe* and *block*, never *substitute*. Any fast path that replaces an LLM
  turn with a prepared action must live in the provider facade's `complete()`.

## 1. Target shape

```
kernel session
 └─ orchestrator mount: HybridOrchestrator            [loop-fast-decisions]   (active rung only)
     └─ upstream.execute(...)  (public Orchestrator contract, nothing else)
         ├─ provider facade RoutedProvider
         │    ├─ complete()  → DecisionService.choose() → fast (synthetic ChatResponse) | real complete()
         │    └─ stream()    → MIRRORED iff the real provider has it; proxied verbatim; fast path OFF
         └─ tool facade ObservedTool → real tool.execute()
 └─ hook mount:  FastDecisionsHook                    [hooks-fast-decisions]  (every rung)
     ├─ observes tool:pre / tool:post / provider:error / provider:request
     ├─ SHADOW SCORER   — "what would we have chosen"     (off the critical path)
     └─ ROLE SCORER     — "what model_role would we propose"  (off the critical path)
 └─ tool mount:  fast_workspace                       [tool-fast-workspace]
 └─ session-scoped, shared by all of the above:
      capability fast_decisions.runtime  → Runtime{service, recorder, shadow worker}
      capability fast_decisions.service  → DecisionService
      channels   fast_decisions.candidates, fast_decisions.questions
```

One rule governs the whole design: **shadow never touches the critical path.** Shadow work is
enqueued and scored on a bounded background worker owned by `Runtime`. That makes "zero behaviour
change in shadow" a structural property, not a claim to be re-argued each release.

## P1 — Provider facade: mirror the transport, never hide it

### Decision

`RoutedProvider` becomes **transport-transparent**:

1. Delete the `stream` / `__wrapped__` blacklist in `__getattr__` (`orchestrator.py:50-53`).
2. `stream` is **not** defined on the class. `__getattr__("stream")` returns a thin async-generator
   wrapper **only when the wrapped provider actually has `stream`**; otherwise it raises
   `AttributeError`, so `callable(getattr(provider, "stream", None))` at `loop-streaming:4614`
   returns exactly what it would return without us.
3. The fast path is attempted **only in `complete()`**. On the `stream` transport the service is
   asked nothing and the turn is byte-identical to no-bundle. Reason code
   `fast_path_unavailable_on_transport`.
4. The synthetic `ChatResponse` construction, identity map, and `parse_tool_calls` special-case stay
   exactly as they are (`orchestrator.py:65-101`) — they are correct.

### Rationale

- §0.2: yielding a synthetic tool call through `stream` cannot work; loop-streaming drops it. Fail
  *closed* (defer to the LLM) rather than fail *open* (drop the action silently). This is the same
  rule the service already applies everywhere else (`service.py:55-58`).
- §0.1: mirroring costs nothing today (no provider has `.stream`) and removes a latent, silent
  regression for any conforming third-party or future provider. The current code lies about the
  Provider protocol (`amplifier_core/interfaces.py:65-128` does not include `stream`, but a provider
  is free to add it, and loop-streaming feature-detects it) — a lie that is invisible until it bites.
- Deleting the blacklist is a **net deletion**. The wrapper exists only to keep telemetry parity on a
  transport nothing currently uses; if the owner prefers, drop the wrapper too and let `__getattr__`
  return the raw bound method — one fewer moving part, at the cost of no `slow_*` events on that
  transport. Specified with the wrapper; the fallback is one line.

### Interfaces

`src/amplifier_fast_decisions/orchestrator.py`

```python
class RoutedProvider:
    def __getattr__(self, name: str):
        if name == "stream":
            inner = getattr(self._provider, "stream", None)
            if not callable(inner):
                raise AttributeError(name)      # mirror absence exactly
            return self._stream_proxy
        return getattr(self._provider, name)

    async def _stream_proxy(self, request, **kwargs):
        """Verbatim proxy of the provider's stream transport.

        The fast path is structurally unavailable here: loop-streaming's
        streaming branch cannot dispatch tool calls (_has_pending_tools
        returns False, :6595). We therefore never ask the service and never
        synthesize a response on this transport.
        """
        service = self._runtime.service
        await service.emit("routed", {
            "route": "slow", "destination": self._provider_key,
            "reason_code": "fast_path_unavailable_on_transport",
            "transport": "provider-stream"})
        start = time.perf_counter()
        await service.emit("slow_start", {... "transport": "provider-stream"})
        try:
            async for chunk in self._provider.stream(request, **kwargs):
                yield chunk
        finally:
            await service.emit("slow_end", {... "transport": "provider-stream",
                                            "duration_ms": ...})
```

- `turn_start` `transport` field becomes `"mirrored"` (we no longer force a transport).
- New `privacy.SAFE_FIELDS` entry: none needed — `transport` and `reason_code` are already allowlisted
  (`privacy.py:23,19`).
- New reason code: `fast_path_unavailable_on_transport`. Document in `docs/EVENTS.md`.

## P2 — Keep wrapping loop-streaming, through its public contract only

### Decision

**Option (a): keep wrapping, contract-only.** Do not write our own orchestrator.

Formalise exactly what we depend on in a new `docs/UPSTREAM_CONTRACT.md` (4 items, below), and add a
real-kernel test that asserts each against the *installed* module — so an upstream change breaks a
test instead of a user session.

### Rationale

- We already use nothing private: the only two touch points are `StreamingOrchestrator(config_dict)`
  (`orchestrator.py:185`) and `await upstream.execute(prompt, context, providers, tools, hooks, **kwargs)`
  (`orchestrator.py:204`). Option (a) is therefore *mostly already true* — the remaining work is
  documentation plus a guard test. Option (b) is not a smaller step; it is a 6707-line purchase.
- What loop-streaming carries that we would have to re-implement and then keep in sync forever:
  steering queue, ephemeral-injection modes, measured-context transactions and rollback, provider
  budget preflight, context-overflow recovery, the `/goal` auto-continue loop, cancellation exits,
  `conversation.provider_pin`, `provider:resolve`. Re-implementing that to add a decision hook is
  exactly the "complexity budget" violation KERNEL_PHILOSOPHY §11 names, and it would make every
  upstream improvement a merge for us.
- Module-dependency hygiene: `modules/loop-fast-decisions/pyproject.toml` already declares
  loop-streaming under an **optional `upstream` extra**, not a hard dependency, and the import is lazy
  inside `__init__` (`orchestrator.py:180-183`). The shipped module's install closure still references
  only core. Keep that shape; do not promote it to a hard dependency.

### The contract we rely on (`docs/UPSTREAM_CONTRACT.md`)

1. `StreamingOrchestrator(config: dict)` — constructor takes one plain dict; unknown keys ignored.
2. `async execute(prompt, context, providers, tools, hooks, **kwargs) -> str` — matches
   `amplifier_core.interfaces.Orchestrator` (`interfaces.py:32-62`); accepts `coordinator=` in kwargs.
3. Transport feature-detection is `callable(getattr(provider, "stream", None))` (`:4614`); the
   `complete()` branch is the one that parses and dispatches tool calls (`:4933-5040`).
4. Tools are invoked as `await tool.execute(tool_call.arguments)` — single positional dict, no kwargs
   (`:6329`) — with `tool:pre` before and `tool:post` after (`:6257`, `:6347`).

Anything outside those four is **not** ours to rely on.

**Event ordering note (must be in the doc).** Our `fast_decisions:turn_start` is emitted in
`HybridOrchestrator.execute` *before* we delegate (`orchestrator.py:195`), so it **precedes**
upstream's `execution:start` (`loop-streaming:3472`). Symmetrically `fast_decisions:turn_end` fires in
our `finally`, *after* `execution:end`. This is deliberate — our events bracket the whole delegation,
including the upstream call itself — but anything correlating the two streams by wall-clock order
needs to know it. Record it in `UPSTREAM_CONTRACT.md` and assert it in the P6 ordering test.

## P3 — Shadow moves into the hook; the orchestrator swap becomes active-only

### Decision

1. `hooks-fast-decisions` gains a **shadow scorer**. On `provider:request` it snapshots state from the
   mounted context manager, collects candidates and questions, and enqueues a scoring job. On
   `tool:pre` it records what the LLM *actually* chose and resolves the pending job into an
   **agreement record**. Nothing it does can change the turn: every handler returns
   `HookResult(action="continue")`, and scoring happens on a background worker.
2. Shadow becomes a config knob on the hook in `behaviors/fast-decisions.yaml`
   (`config: {mode: shadow, ...}`). The root `bundle.md` therefore *is* the shadow rung: compose
   fast-decisions onto any bundle, keep your orchestrator, get shadow.
   **`bundles/shadow.yaml` is NOT deleted.** It is retained for one release cycle as a *deprecated
   forwarding bundle*: it includes the root `bundle.md` and sets the shadow knob, and it **no longer
   swaps `session.orchestrator`**. Existing `amplifier bundle add <...>/bundles/shadow.yaml` URLs keep
   working and quietly get the better implementation. Its `bundle.description` opens with
   `DEPRECATED — compose bundle.md (or behaviors/fast-decisions) instead; removed in 0.3.0.`
3. `bundles/active.yaml` survives as the only standalone bundle that swaps the orchestrator, because
   swapping `session.orchestrator` is a root-bundle concern (BUNDLE_GUIDE: a behavior is a slice, it
   does not define a session).
4. **Policy ownership keeps the already-merged `owner=True` mechanism** (`runtime.py:41-55`). The
   orchestrator owns policy; the hook attaches to whatever runtime exists. No rank, no new mechanism.
   The prose at `runtime.py:47-53` — "mount order across module types is a kernel implementation
   detail, not a contract" — is **wrong and must be corrected**: mount order *is* a documented,
   guaranteed kernel contract (see Rationale). Rewrite that comment to say the re-apply is
   *defensive*, covering out-of-session construction (tests, `afast demo`, a future host), not an
   intra-session race.
5. The `allow_external_state` privacy gate is unchanged and still gates every call to Jev
   (`service.py:68-69`). What changes is the **shipped default for the shadow rung**: shadow with
   `allow_external_state: true` is a first-class, documented rung, reachable via the existing
   `afast configure --mode shadow --allow-external-state` (`cli.py:87` only blocks *active* without
   the flag). Rung ladder becomes: `off` → `shadow, external=false` (deterministic only) →
   `shadow, external=true` (real Jev, zero behaviour change) → `active`.

### Rationale

- The owner wants shadow measurement before any behaviour change. Requiring an orchestrator swap to
  *measure* couples the measurement to the riskiest change in the system. Put it in the hook and it
  composes onto **any** orchestrator, including ones that do not exist yet.
- §0.3: the hook cannot see the request from `provider:request`. It must read the context manager —
  a public kernel mount point, `coordinator.get("context")` (`_engine.pyi:214`), returning a
  `ContextManager` with `get_messages()` (`interfaces.py:202-204`). That view is the pre-overlay
  message list: close to, not identical to, what the orchestrator dispatches (injections and
  compaction overlays are applied later, `loop-streaming:4340-4560`). That difference is real and
  must be *recorded*, not hidden: every shadow record carries
  `state_source: "context_mount" | "provider_complete"`. An eval that mixes the two without the
  discriminator would be measuring two different things.
- Running shadow on a background worker is what makes "zero behaviour change" checkable rather than
  argued. It also makes the P4 router free of latency risk.
- **Mount order is a kernel contract, so no race exists to solve.** `_session_init.py` loads
  orchestrator (`:74`) → context (`:104`) → providers (`:154`) → tools (`:222`) → hooks (`:248`),
  and `@core:CONTRACTS.md` §Module Lifecycle states this ordering "is stable and guaranteed". The
  orchestrator therefore *always* builds the runtime before the hook mounts, within a session. An
  earlier draft of this spec proposed a rank mechanism to arbitrate that ordering; it was solving a
  race that cannot occur, and has been dropped. `owner=True` stays, and the one test that covers
  reversed construction is kept and **relabelled as defensive** — it guards non-session construction
  paths (unit tests, `afast demo`, a future non-kernel host), not a real intra-session ordering risk.

### The snapshot is on the critical path. The scoring is not.

`hooks.emit` applies **no per-handler timeout** — a slow handler slows the turn. In the hook, only
*scoring* is deferred to the worker; the **snapshot** (`await context.get_messages()`, candidate
collection, question collection, hashing) necessarily runs inside the handler, on the critical path.
That work must therefore be hard-bounded, not merely "expected to be fast":

| Bound | Config key | Default | Behaviour when exceeded |
|---|---|---|---|
| Messages read from the context mount | `shadow_max_messages` | `12` | take the last N; never walk the full history |
| Total snapshot characters | `max_state_chars` (existing, `contracts.py:108`) | `12000` | drop oldest observations (existing loop, `state.py:63-64`) |
| Wall-clock budget for the whole snapshot | `shadow_snapshot_budget_ms` | `25` | abandon the snapshot, emit `fast_decisions:fallback` with `reason_code: shadow_snapshot_budget_exceeded`, return `continue` |

The budget is enforced with `asyncio.timeout` around the snapshot only. Exceeding it is a normal,
counted outcome — never an exception into the hook chain. `shadow_snapshot_budget_exceeded` is
reported by `afast bench` as a stability metric: if it fires often, shadow is lying about its
own overhead and the operator needs to see that.

async def mount(coordinator, config: dict):
    # owner=False (the default): the orchestrator mounts first per the kernel
    # lifecycle contract and owns Policy. When no orchestrator is present -- the
    # normal shadow rung -- this call builds the runtime and this config's Policy
    # applies, which is exactly what the shadow rung wants.
    runtime, owner = get_runtime(coordinator, config)
    scorer = ShadowScorer(runtime, coordinator, config)
    registrations = [
        coordinator.hooks.register("provider:request", scorer.on_provider_request, priority=999),
        coordinator.hooks.register("tool:pre",  scorer.on_tool_pre,  priority=999),
        coordinator.hooks.register("tool:post", scorer.on_tool_post, priority=999),

        coordinator.hooks.register("execution:end", scorer.on_execution_end, priority=999),

## P4 — The fast router: model-role proposals, shadow-only

### Decision

A second consumer of the same `DecisionService`, living in the same hook, that at **delegation time**
proposes a `model_role` — and records it next to what actually happened. It never mutates anything.

Mechanics:

1. Trigger: `tool:pre` where `data["tool_name"] == "delegate"` (payload shape:
   `{"tool_name", "tool_call_id", "tool_input", "parallel_group_id"}`, `loop-streaming:6258-6264`).
2. **Abstain immediately** when `tool_input.get("model_role")` is non-empty → reason
   `explicit_role_present`. Explicit user/agent choice wins, full stop.
3. Resolve the live role set **once per session**, lazily: read capability
   `model_role_resolver` (`coordinator.get_capability("model_role_resolver")`); take
   `known_roles` if present and type-guarded as a sequence of `str` (it is optional —
   `resolver_class.py:37-45` is explicit that absent ≠ "no resolver"); for each, `await
   resolver.resolve(role)` and keep the roles returning a non-empty `list[ProviderPreference]`.
   Cache the result on `Runtime`. If the capability is absent, or `known_roles` is absent, or the
   probe raises or exceeds `role_probe_timeout_ms` → the router is permanently disabled for the
   session with reason `role_resolver_unavailable`. No guessing at role names.
4. Build a `Question` of type `choice` whose criteria are the live roles plus `reason` (abstain), with
   the delegate's `agent` / `prompt` head as state, and enqueue a `kind="role"` `ShadowJob`.
5. On the matching `tool:post`, join and emit `fast_decisions:role_agreement`.
6. `conversation.provider_pin` is **never read and never written**. We propose a *role*; the
   resolver, and only the resolver, maps a role to provider/model. A pin binds the conversation
   provider (`loop-streaming:6628-6641`) and is orthogonal — recording that we never touch it is
   part of the contract, and the test below enforces it.

### Rationale

- §0.3: `modify` is not honored at `tool:pre`, so an "active" router through this seam is impossible
  today. Shadow-only is not a staging choice here — it is the only honest option. Going active later
  requires either an upstream change in loop-streaming or moving the router into the delegate tool's
  own resolution path; both are out of scope and named in Non-Goals.
- Latency: `resolver.resolve()` can issue `list_models()` network calls the first time per provider
  (cached thereafter, `resolver_class.py:152-171`). Putting that probe on the `tool:pre` critical path
  would tax every delegate. Because the router is shadow-only, the whole thing runs on the P3 shadow
  worker and costs the turn nothing. This is the payoff for making shadow structurally off-path.
- Measuring "would a cheap role have sufficed" is the cleanest available proxy for the owner's Return
  on Inference metric, and it needs no behaviour change to collect.

## P5 — Contribution channels: candidates and questions, one batched request

### Decision

Two channels, both collected with the kernel API `register_contributor(channel, name, callback)` /
`await coordinator.collect_contributions(channel)` (`_engine.pyi:224-228`). Contributor callbacks take
**no arguments** (kernel contract) and return a list.

- `fast_decisions.candidates` — prepared actions. Already exists (`contracts.py:13`,
  `candidates.py:40-52`); keep, tighten validation.
- `fast_decisions.questions` — **new**. Bounded judgment questions evaluated in the *same* backend
  request as the action choice.

### Batching is VERIFIED, not assumed

Confirmed against `docs.typesafe.ai/api`, `docs.typesafe.ai/cookbooks/parallel_questions`, and
`typesafe-sdk 0.6.0`. The design below is shaped to **this exact API**, not to a guess:

```python
response = await client.system_one(
    state=<str | dict | list>,                       # our bounded state snapshot
    questions={"next_action": Choice(...), "risk": Score(...), "stale": Noul(...)},
    model="jev-latest",
)
response.answers["next_action"].probabilities    # dict[label, float]
response.answers["next_action"].confidence       # float — Choice and Score only
response.answers["stale"].noul                   # float — Noul questions
response.usage.input_tokens / .output_tokens
```

Facts that constrain the design:

- **One request carries many questions**, and questions are **scored independently** — batching does
  not change any individual answer. So batching is a pure latency/cost win, with no accuracy
  trade-off to measure. This is the single fact the whole "one request per state" requirement rests on.
- `Choice` supports **≤ 255 alternatives**; our `max_candidates ≤ 63` (`contracts.py:121-122`) is
  already well inside it.
- **No documented cap on questions per request**; the cookbook batches 13. We cap at `max_questions: 8`
  by policy, not by API limit — a bound we chose and can raise with evidence.
- Rate limits: **250k tokens/s**, **1,200 req/min**. The SDK retries with backoff honouring
  `retry-after`. We continue to construct the client with `RetryPolicy(max_retries=0)`
  (`backends.py:32`) because a retry inside a 750 ms decision deadline is a worse outcome than a
  clean fall-back to the LLM — fail closed, not late.
- Pricing: **$0.042 / M input tokens, $0 output**. This makes `decision_cost_usd` directly computable
  in the bench (P7) rather than reported as a bare token count.
- Terminology: the third primitive is **`Noul`**, not "boolean". Our `QuestionType` literal uses
  `"noul"` to match the vendor, so nobody has to maintain a translation table.

The backend interface changes from one hard-coded question to a batch:

```python
# contracts.py
QuestionType = Literal["choice", "score", "noul"]   # vendor primitives, vendor names

@dataclass(frozen=True)
class Question:
    name: str                       # ^[a-z][a-z0-9_]{0,31}$ ; "next_action" is RESERVED
    type: QuestionType
    instructions: str               # <= 512 chars, scrubbed
    criteria: dict[str, str] = field(default_factory=dict)   # choice only; 2..255 entries
    origin: str = "contributed"

@dataclass(frozen=True)
class DecisionRequest:
    state: dict[str, Any]
    candidates: tuple[Candidate, ...]
    questions: tuple[Question, ...]          # never includes next_action; the service adds it

@dataclass(frozen=True)
class Answer:
    """One question's result. `probabilities` for choice/score, `noul` for noul."""
    probabilities: dict[str, float] = field(default_factory=dict)
    confidence: float | None = None          # choice/score only
    noul: float | None = None                # noul only

@dataclass(frozen=True)
class DecisionResult:
    action: Decision                          # the next_action choice (existing Decision type)
    answers: dict[str, Answer]                # contributed questions, by name
    model: str = "unknown"
    input_tokens: int | None = None
    output_tokens: int | None = None
    synthetic: bool = False

class DecisionBackend(Protocol):
    name: str
    external: bool
    async def ask(self, request: DecisionRequest) -> DecisionResult: ...
    async def close(self) -> None: ...
```

`JevBackend.ask` builds **one** `system_one(state=..., questions={...}, model=...)` call containing
`next_action` plus every contributed question (`backends.py:36-59` already has the single-question
shape; this generalises it) and maps `response.answers[...]` back by name. One request per state —
the batching requirement, satisfied structurally rather than by convention.

`DecisionBackend.decide` is **replaced**, not kept alongside `ask`. There are three implementations
(`JevBackend`, `UnavailableBackend`, `ScriptedBackend`) and no external consumers; a compatibility
shim here would be complexity paying rent to nobody.

### Validation, dedup, bounds

Applied in `candidates.collect_candidates` and a new `questions.collect_questions`, both inside the
existing shared deadline (`service.py:74`):

1. **Shape**: a contribution must be a `list`; non-list contributions are dropped with
   `contribution_shape_invalid` (counted, not raised — one bad contributor must not break the turn).
2. **Identity**: candidate ids match `^[A-Za-z][A-Za-z0-9_-]{0,63}$` and may not be `reason`
   (existing, `contracts.py:60-61`). Question names match `^[a-z][a-z0-9_]{0,31}$` and may not be
   `next_action`.
3. **Dedup**: keyed by id/name. Identical fingerprint → silently collapsed. **Conflicting** fingerprint
   for the same id → the whole contributed set from that contributor is dropped and
   `contribution_conflict` is recorded. (Today a conflict raises and kills the decision,
   `candidates.py:68-69`; that lets one misbehaving module disable the fast path globally. Downgrade
   to per-contributor rejection.)
4. **Bounds**: `max_candidates` (default 12, existing) and `max_questions` (default 8, new). Over the
   bound → truncate deterministically by `(contributor_name, id)` sort order and record
   `contribution_truncated`. A `choice` question needs 2..255 criteria (vendor limit); outside that
   range it is dropped with `question_criteria_invalid`.
5. **Arguments**: deep-copied at the boundary through canonical JSON (existing, `candidates.py:22-30`),
   16 KiB cap (existing, `contracts.py:65-66`).
6. **Authority**: a contribution is *extensibility, never permission*. Eligibility still requires
   allowlist + tool-present + validator (`service.py:31-42`). Unchanged, and re-stated in the doc
   because it is the property most likely to be eroded by a future contributor.

### Payload schemas (documented in `docs/EXTENDING.md`)

### Decision

### (i) Offline replay eval

`afast bench replay --events DIR [--session ID] [--out report.json] [--md report.md]`

Input: the existing `fast_decisions:*` JSONL (`telemetry.py:21-77`). Zero network, zero LLM. Joins

Metrics (all reported with `n` and, where applicable, a 95% bootstrap interval; **never a point
estimate alone**):

| Metric (exact emitted name) | Block | Definition |
|---|---|---|
| `decision_latency_ms_p50` / `decision_latency_ms_p95` | `decision` | from `scored.duration_ms` (`latency_kind == "decision_model_wall_time"`) |

### What a UAT session looks like

1. `afast doctor --require-amplifier` → all required checks green.
2. `afast configure --mode shadow --allow-external-state --workspace <repo>` → local profile.
3. Run a normal working session, 30–60 minutes, ordinary tasks. **Nothing should feel different.**
   That is the acceptance criterion for the rung.
4. `afast bench replay --events ~/.amplifier/fast-decisions/events --md uat.md`.
5. The owner reads `uat.md` and answers one question: *would I have let it act?* — per decision, for a
   sample of ~20 mismatches.
6. Only if agreement and calibration hold does `--mode active` get considered, and only for
   `fast_workspace`.

### What the observatory viewer must show

The viewer (`server.py`, `cli.py serve`) currently renders the event stream. For UAT it must add
exactly four things — no more:

1. **A decision list**, one row per `decision_id`: proposed vs actual, agreement, probability, margin,
   latency, reason code. Sortable by mismatch-first.
2. **A reliability plot**: 10 bins, stated probability (x) vs empirical correctness (y), with the
   diagonal drawn. This is the single most decision-relevant view and is currently absent.
3. **A rung banner**: mode, backend, `allow_external_state`, policy version — so nobody ever reasons
   about a run whose configuration they have guessed.
4. **A "what would have changed" counter**: avoided LLM turns and, separately, mismatches that would
   have produced a *different action* — kept visually distinct, because they are different risks.

No control endpoint, no browser-to-agent channel — unchanged from today.

(`~/.local/share/uv/tools/amplifier/bin/python3 -m unittest discover -s tests`), which has
`amplifier_core` 1.6.1 and the installed `loop-streaming`. The offline lane
(`python3 -m unittest discover -s tests -v`, per `AGENTS.md`) also runs on every PR and skips the
real-kernel tests via the existing `HAS_CORE` guard (`test_kernel_validation.py:31`). A PR is green
only when both lanes pass. DTU checks are a third, manual gate at the owner's review — never a
substitute for the `upstream` job.

## Non-goals

Explicitly **not** in this redesign:

1. **Any change to `amplifier-core`.** Not a patch, not a PR, not a vendored copy.
2. **Our own orchestrator implementation.** P2 decided against it; revisit only if the upstream
   contract tests (PR A) start failing repeatedly.
3. **An active fast path on the `.stream` transport.** Structurally impossible today (§0.2). Reaching
   it requires an upstream change in loop-streaming, a separate proposal with its own acceptance
   criteria.
4. **An active model-role router.** `modify` is not honored at `tool:pre` (§0.3). Shadow-only until
   either upstream honors it or the router moves inside `tool-delegate`'s own resolution path.
5. **Touching `conversation.provider_pin`, or overriding any explicit user/agent model choice.** Ever.
6. **Widening `allowed_tools` beyond `fast_workspace`.** Decided, not merely deferred — see
   Decision 1 below.
7. **A rank/priority mechanism for policy ownership.** Mount order is a kernel contract; the race
   does not exist.
8. **Local Jev weights, learned candidate generation, autonomous stopping, plan synthesis.**
9. **A wildcard hook subscription.** One registration per explicit event name.
10. **Claiming measured speedup.** The bench projection is labelled a model. No ratio is presented as
    measured whole-task acceleration until a controlled A/B exists.
11. **Removing the `allow_external_state` gate**, or defaulting it to `true` in any shipped file.

## Decisions taken (formerly open questions)

**1. First active rung — DECIDED (owner, to confirm at gate).** Active mode stays limited to
**prepared read-only `fast_workspace` actions**, exactly as today. The model-role router is
**shadow-only** and ships off by default.

*Rationale.* The two candidates are not comparable in risk. The `fast_workspace` path is read-only,
revision-checked, validator-gated and allowlisted — its worst case is a wasted read. The router's
worst case is a silently cheaper model on real work, which is both harder to detect and harder to
attribute. Separately, §0.3 makes an active router impossible through the current seam anyway, so
"router first" would mean an upstream dependency before any value lands. Keeping active narrow also
keeps `decision.unsafe_autonomous_actions` trivially auditable: any non-`fast_workspace` fast-path
submission is a bug by construction, not a judgement call. We are **not** opening an upstream
loop-streaming issue for `modify`-at-`tool:pre` yet — shadow data should justify it first.

**2. TypeSafe Jev batched-question API — RESOLVED.** Verified against `docs.typesafe.ai/api`,
`/cookbooks/parallel_questions`, and `typesafe-sdk 0.6.0`. One request carries many independently
scored questions; `Choice` ≤ 255 alternatives; no documented question cap (13 batched in the
cookbook); 250k tokens/s and 1,200 req/min; SDK retries honour `retry-after`; $0.042/M input, $0
output. P5 is shaped to this exact API, and `QuestionType` uses the vendor's `noul` name. Batching
does not change answers, so it is a pure latency/cost win.

**3. CLASSic metric identifiers — RESOLVED.** Verified against
`michaeljabbour/amplifier-eval-taxonomies`, `modules/hooks-eval-metrics/.../models.py`. The bench
emits a `CLASSicMetrics.to_dict()`-shaped JSONL record and joins on `session_id`, adding a `decision`
sub-block and populating the taxonomy's `accuracy_proxy` escape hatch. The earlier `classic.*` prefix
scheme is dropped — it was a guess, and it would have required the mapping layer this resolution
removes.

**No open questions remain.** Anything discovered during implementation that needs a design call
comes back to this document as an amendment, not a silent choice in code.
